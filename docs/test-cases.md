# Лабораторная работа №2 — тест-кейсы к UC-01 «Добавление переговорной комнаты»

**Объект:** Booking PZ, форма `GET /add` и операция `POST /add`.  
**Источник требований:** [UC-01](use-case-UC-01.md), `config/validationSettings.json`, `routes/webRoutes.js`, `validation/webRoom.js`.  
**Набор:** **12 осмысленных ручных тест-кейсов** (позитивные, негативные, граничные значения, доступ и сохранение).  
**Состояние на момент подготовки:** фактические результаты локального ручного прогона ещё не предоставлены; поэтому везде **Not Run**, а не придуманное Passed.

## 1. Анализ требований и тест-дизайн

Мы группируем однотипные входные значения **внутри одного тест-кейса**. Например, четыре значения вместимости проверяют *одно требование* «целое число от 1 до 1000», а не образуют четыре независимые цели тестирования. При этом результат каждого набора входных данных фиксируется отдельно.

### Поля и классы эквивалентности

| Поле | Допустимый класс | Недопустимый класс | Границы, которые проверяем | Связанные тесты |
|---|---|---|---|---|
| `name` | Непустой текст, 1–100 символов | Пустое/пробельное значение, 101+ символ | 1, 100, 101 | TC-03, 04, 05 |
| `roomNumber` | Уникальный текст, 1–20 символов | Отсутствует, 21+ символ, уже занят | 1, 20, 21; дубликат | TC-03, 06, 10 |
| `location` | Непустой текст, 1–150 символов | Отсутствует, 151+ символ | 1, 150, 151 | TC-03, 05 |
| `floor` | Целое число 1–100 | Отсутствует, меньше 1, больше 100, дробь | 0, 1, 100, 101 | TC-03, 07 |
| `capacity` | Целое число 1–1000 | Отсутствует, меньше 1, больше 1000, дробь | 0, 1, 1000, 1001; 2.5 | TC-03, 08, 09 |
| `description` | Необязательный текст до 2000 символов | 2001+ символ | пусто, 2000, 2001 | TC-02, 05 |

**Таблица решений по доступу:** неавторизованному посетителю запрещён `POST /add` (302 на `/login`); учебному пользователю `role=user` запрещён (403); учебному администратору `role=admin` разрешён при корректных данных (303 после создания). См. TC-01, 11, 12.

## 2. Среда и правила выполнения

**Общие предусловия для TC-01—TC-10:** Node.js-сервер и PostgreSQL запущены, приложение открывается по `http://localhost:3000`. Для отправки форм администратор использует учебную ссылку `/add?auth=1&role=admin`. Это **имитация авторизации параметрами URL**, не реальная защищённая аутентификация.

**Корректные базовые данные (B):**

| Поле | Значение |
|---|---|
| `name` | `Переговорная Тест` |
| `roomNumber` | Новый уникальный номер вида `LAB2-001` |
| `location` | `Главный корпус` |
| `floor` | `2` |
| `capacity` | `10` |
| `description` | `Учебная комната` |

В каждом новом **позитивном** отправлении используйте свободный `roomNumber` (`LAB2-001`, `LAB2-002` и т. д.), иначе проверка сработает как дубликат и исказит результат. Для *негативных* отправлений тоже удобно использовать новый номер, чтобы убедиться, что запись действительно не создана. Перед началом можно записать количество комнат или проверить отсутствие конкретного номера.

**Базовые шаги:** открыть форму как администратор → ввести B с указанным изменением → отправить → посмотреть код и текст ответа в DevTools/Network (или Postman) → проверить список комнат `/?auth=1&role=admin` и, если запись создана, её карточку `/item/:id?auth=1&role=admin`. Для недопустимых значений, которые блокирует браузер (`required`, `min`, `max`, `maxlength`), отправлять HTTP-запрос через Postman с типом `x-www-form-urlencoded`; это проверяет **серверную**, а не только клиентскую валидацию.

**Важно про коды:** корректный `POST /add` возвращает **303 See Other**, но браузер после автоматического перехода покажет страницу списка с **200 OK**. Проверяйте именно исходный запрос `POST`, не только итоговую страницу. При HTTP 400/403/302 данные в БД не должны появиться.

**Статусы:** Passed — результат совпал; Failed — есть несоответствие; Blocked — нельзя выполнить; Skipped — сознательно пропущено; Not Run — ещё не выполняли. Для составных тест-кейсов отметьте фактический результат каждой строки набора. **Весь кейс = Passed только если все его обязательные варианты пройдены.**

## 3. Ручные тест-кейсы

### TC-01 — Успешное создание и сохранение комнаты

- **Приоритет:** High. **Техника:** позитивный функциональный сценарий.
- **Предусловия:** общие; указанный номер отсутствует в списке.
- **Данные:** B, новый номер `LAB2-001`.
- **Шаги:** (1) открыть форму администратора; (2) заполнить поля; (3) нажать «Добавить»; (4) открыть список и карточку созданной комнаты.
- **Ожидаемый результат:** `POST` возвращает **303** и перенаправляет на список; запись появилась **ровно один раз**, а название, номер, расположение, этаж, вместимость и описание совпадают с введёнными.
- **Постусловия:** создана одна новая запись Rooms.
- **Фактический результат:** _не заполнен_. **Статус:** Not Run.

### TC-02 — Создание без необязательного описания

- **Приоритет:** Medium. **Техника:** класс эквивалентности «необязательное поле отсутствует».
- **Предусловия:** общие; новый номер.
- **Данные:** B, `description` не передаётся (или пустая строка).
- **Шаги:** (1) открыть форму; (2) заполнить обязательные поля; (3) оставить «Описание» пустым; (4) отправить; (5) проверить карточку записи.
- **Ожидаемый результат:** **303**; комната добавлена; описание сохранено пустым, обязательные данные не потеряны.
- **Постусловия:** создана одна комната.
- **Фактический результат:** _не заполнен_. **Статус:** Not Run.

### TC-03 — Обязательные поля нельзя пропустить

- **Приоритет:** High. **Техника:** классы эквивалентности «поле отсутствует».
- **Предусловия:** общие; для каждого варианта — новый номер, кроме намеренно отсутствующего.
- **Шаги:** (1) взять B; (2) убрать ровно **одно** обязательное поле; (3) отправить `POST /add?auth=1&role=admin` через Postman; (4) проверить код, сообщение и отсутствие новой записи; (5) повторить для следующего поля.
- **Ожидаемый результат для каждого варианта:** **400 Bad Request**, понятное сообщение об обязательном поле; новая комната не создаётся.
- **Постусловия:** новых записей нет.

| Вариант | Отсутствующее поле | Ожидаемое сообщение содержит | Фактически | Статус |
|---|---|---|---|---|
| A | `name` | `Название: поле обязательно` | — | Not Run |
| B | `roomNumber` | `Номер комнаты: поле обязательно` | — | Not Run |
| C | `location` | `Расположение: поле обязательно` | — | Not Run |
| D | `floor` | `Этаж: требуется целое число` | — | Not Run |
| E | `capacity` | `Вместимость: требуется целое число` | — | Not Run |

**Общий статус TC-03:** Not Run.

### TC-04 — Название только из пробелов

- **Приоритет:** Medium. **Техника:** негативный класс «содержит символы, но после trim пусто».
- **Предусловия:** общие.
- **Данные:** B, `name="   "`.
- **Шаги:** (1) заполнить форму; (2) заменить название тремя пробелами; (3) отправить; (4) проверить ответ и отсутствие записи.
- **Ожидаемый результат:** **400**, сообщение `Название: поле обязательно`; комната не создаётся.
- **Постусловия:** новых записей нет.
- **Фактический результат:** _не заполнен_. **Статус:** Not Run.

### TC-05 — Граничная длина текстовых полей

- **Приоритет:** Medium. **Техника:** анализ граничных значений.
- **Предусловия:** общие; свободный номер для каждого допустимого варианта.
- **Данные:** B, меняется только одно текстовое поле.
- **Шаги:** (1) сформировать строку указанной длины (например, повторить букву `А` нужное число раз); (2) отправить форму/POST; (3) проверить код и сохранение/отказ; (4) повторить для остальных наборов.
- **Ожидаемый результат:** в пределах ограничения — **303** и сохранённая строка той же длины; выше максимума — **400**, комната не создана.
- **Постусловия:** появляются только записи от допустимых наборов.

| Вариант | Поле | Количество символов | Ожидаемо | Фактически | Статус |
|---|---|---|---|---|---|
| A | `name` | 1 (минимум) | 303, создана | — | Not Run |
| B | `name` | 100 | 303, создана | — | Not Run |
| C | `name` | 101 | 400, отказ | — | Not Run |
| D | `location` | 1 (минимум) | 303, создана | — | Not Run |
| E | `location` | 150 | 303, создана | — | Not Run |
| F | `location` | 151 | 400, отказ | — | Not Run |
| G | `description` | 2000 | 303, создана | — | Not Run |
| H | `description` | 2001 | 400, отказ | — | Not Run |

Для значений 101, 151 и 2001 обходите браузерный `maxlength` через Postman. Строки состоят только из букв, **без пробелов по краям**, иначе `trim` изменит длину. Для допустимых строк проверяйте полное сохранение, а не только HTTP-код.

**Общий статус TC-05:** Not Run.

### TC-06 — Длина номера комнаты

- **Приоритет:** Medium. **Техника:** границы для уникального идентификатора комнаты.
- **Предусловия:** общие; номера тестовых записей свободны.
- **Данные:** B, меняется `roomNumber`.
- **Шаги:** (1) отправить каждый вариант; (2) проверить код и факт создания/отказа.
- **Ожидаемый результат:** длина 1 или 20 — **303**; 21 — **400**; ошибочная запись отсутствует.
- **Постусловия:** созданы только комнаты с допустимой длиной номера.

| Вариант | Длина `roomNumber` | Ожидаемо | Фактически | Статус |
|---|---|---|---|---|
| A | 1 (например, `Z`) | 303 | — | Not Run |
| B | 20 (уникальная строка) | 303 | — | Not Run |
| C | 21 | 400 | — | Not Run |

**Общий статус TC-06:** Not Run.

### TC-10 — Номер комнаты должен быть уникальным

- **Приоритет:** High. **Техника:** проверка бизнес-ограничения уникальности.
- **Предусловия:** общие.
- **Данные:** B, фиксированный прежде неиспользованный номер (например, `LAB2-DUP`).
- **Шаги:** (1) создать комнату с этим номером; (2) убедиться, что она появилась; (3) повторно отправить корректную форму с **тем же номером**, но другим названием; (4) проверить список/число записей.
- **Ожидаемый результат:** первый запрос **303**; второй — **400** с сообщением `Комната с таким номером уже существует.`; в БД и списке остаётся **ровно одна** комната с указанным номером, а её данные не изменены повторным запросом.
- **Постусловия:** одна запись с тестовым номером.
- **Фактический результат:** _не заполнен_. **Статус:** Not Run.

### TC-11 — Обычному пользователю запрещено добавлять комнаты

- **Приоритет:** High. **Техника:** разграничение прав.
- **Предусловия:** приложение доступно, используется учебная роль `user`.
- **Данные:** B, свободный номер.
- **Шаги:** (1) открыть `GET /add?auth=1&role=user`; (2) убедиться, что форма не открывается; (3) напрямую отправить корректный `POST /add?auth=1&role=user`; (4) проверить отсутствие записи.
- **Ожидаемый результат:** и GET, и POST возвращают **403 Forbidden**; форма добавления недоступна, запись не создаётся.
- **Постусловия:** новых записей нет.
- **Фактический результат:** _не заполнен_. **Статус:** Not Run.

### TC-12 — Без авторизации нельзя добавлять комнаты

- **Приоритет:** High. **Техника:** контроль доступа при отсутствии учебной сессии.
- **Предусловия:** приложение доступно, **параметров** `auth=1&role=admin` нет.
- **Данные:** B, свободный номер.
- **Шаги:** (1) открыть `GET /add`; (2) отправить корректный `POST /add` без `auth` и `role`; (3) проверить редирект и отсутствие записи.
- **Ожидаемый результат:** оба запроса возвращают **302 Found**, `Location: /login`; создать комнату без роли нельзя.
- **Постусловия:** новых записей нет.
- **Фактический результат:** _не заполнен_. **Статус:** Not Run.

## 4. Как фиксировать фактические результаты

По **каждой строке** составных TC-03, 05, 06, 07, 08 записать фактический HTTP-код, результат сохранения и статус. Для остальных TC достаточно отдельной записи по сценарию. В `docs/test-report.md` свести результаты 12 кейсов и найденные дефекты; для составного кейса `Passed` ставить только после успешного выполнения **всех** строк.

Если результат отличается от ожидаемого, отметить **Failed** и создать дефект с: шагами воспроизведения, входными данными, ожидаемым и фактическим поведением, номером версии/коммита, скриншотом или HTTP-ответом.

После положительных тестов удалить созданные комнаты через интерфейс администратора (или использовать отдельную тестовую БД), чтобы тестовые данные не мешали новым прогонам. **Не удалять демонстрационные или чужие данные.**

## 5. Автоматические тесты — отдельный уровень

В `tests/webRoom.test.js` сохранены **32 автоматические модульные проверки** работы `validateWebRoom()`. Запуск: `npm test` (без PostgreSQL). Эти проверки не открывают браузер, не обращаются к `POST /add`, не проверяют запись в PostgreSQL и не заменяют ручные интеграционные сценарии выше. Для результатов автоматического прогона существует отдельная строка в отчёте.
